# Nagi の判断の記録

開発中に出た判断の要る点を、質問、選んだ答え、ほかにあった選択肢の形で残す。新しいものを下に足す。

## 2026-11-18

### 土台をどう作るか

- **質問:** Nagi を何の上に作るか。
- **答え:** google/mozc をフォークする。Mozkey(koyasi777/mozkey)は実装の手本として読む。
- **ほかの選択肢:**
  - Mozkey をフォークする。気に入っている挙動がそのまま残るが、自分で作る部分が減る。
  - 外側を Swift で一から書き、変換だけ Mozkey のものを外から呼ぶ。検証したところ、Mozkey の補強辞書はリポジトリに含まれず手元で生成する仕組みで、変換部分だけのビルドが通らなかった。
- **決めた人:** 作者。

### 対象の OS

- **質問:** Windows と Linux のコードを消すか。
- **答え:** 消さない。対象は Apple Silicon の Mac だけだが、ほかの OS のコードは Mac 向けのビルドでは使われない。消すと本家の取り込みで衝突するだけになる。
- **ほかの選択肢:** 消して Mac 専用のツリーにする。本家への追従をやめると決めたときに行えばよい。

### 辞書

- **質問:** 辞書をどう持つか。
- **答え:** Mozc の標準辞書を使う。既存の OSS 辞書をスクリプトで取り込むのはよい。Nagi 独自の辞書を作って手で保守することはしない。
- **ほかの選択肢:** 独自の単語リストを育てる。保守の負担が続くので採らない。
- **決めた人:** 作者。

### GitHub 上の形

- **質問:** リポジトリを google/mozc のフォークとして作るか。
- **答え:** 公開のフォークにする。本家は `upstream`、自分の push 先は `origin`。作業ブランチは `main`。
- **ほかの選択肢:** フォーク表示のない非公開リポジトリに履歴ごと push する。取り込みは同じようにできるが、作者がフォーク表示のある見た目を選んだ。

### 名前と識別子

- **質問:** Mozc や Mozkey と同じ Mac に並べて入れるために、何を変えるか。
- **答え:** アプリ名を `Nagi`、識別子の接頭辞を `org.nagi.inputmethod.Japanese`、設定フォルダを `~/Library/Application Support/Nagi`、パッケージの識別子を `org.nagi.pkg.JapaneseInput` にする。ソース内の名前空間、ビルドターゲット名、`BRANDING` は `Mozc` のまま残す。
- **ほかの選択肢:**
  - 接頭辞を `io.github.<アカウント名>.nagi` にする。持っているドメインに基づく正しい逆引き形式だが、アカウント名を変えると識別子も変わる。
  - ソース内の名前もすべて `Nagi` に置き換える。本家の取り込みのたびに衝突するので採らない。
- **根拠:** Mozkey と Mozless が同じやり方で並行インストールを実現している。

### Bazel がヘッダーの変更を拾わない件

- **質問:** この開発環境(Xcode 27.2、Bazel 9.0.2)では、`.h` を書き換えても、それを取り込む `.cc` や `.mm` が再コンパイルされない。`base/const.h` の名前を変えたのに、古い名前が実行ファイルに残った。`.cc` の変更は正しく検知される。どう対処するか。
- **答え:** ヘッダーを書き換えたあとは、自前コードのオブジェクトを消してからビルドする。

  ```sh
  cd src
  find -L bazel-out/ -path '*/_objs/*' -name '*.o' -not -path '*/external/*' -delete
  ```

  名前や識別子に関わる変更のあとは、展開したパッケージの実行ファイルを `strings` で検査して確かめる。
- **ほかの選択肢:**
  - 毎回 `bazelisk clean` する。確実だが、全体のビルドに 10 分以上かかる。
  - 原因を突き止めて直す。コンパイル処理の入力にはヘッダーが宣言されており、Bazel の再起動やファイル監視の切り替えでも直らなかった。原因は未特定で、後回しにした。

### ライブ変換の作り

- **質問:** 遅延付きライブ変換を、どの層にどう入れるか。
- **答え:** Mozc に元からある「遅延コールバック」(`Output.callback` と `delay_millisec`)を使う。キー入力のたびにセッションが `APPLY_LIVE_CONVERSION` を予約し、クライアントが待ち時間のあとに送り返す。キーごとに世代番号を進め、古い予約は捨てる。
- **ほかの選択肢:**
  - クライアント側だけで変換を呼ぶ。セッションの状態と食い違いやすい。
  - Mozkey の実装を取り込む。セッション層だけで 5 万行を超える差分があり、自分で作る方針に合わない。
- **決めたルール:**
  - プレビュー中の文字入力、Backspace、Delete は、読みに対する編集として扱う。
  - Space、文節の操作、確定は通常の変換として扱い、以後は書き換えない。
  - Esc でかなに戻した読みは、読みが変わるまで自動では変換し直さない。
  - 読みが最小文字数より短いとき、ローマ字が途中のときは変換しない。
- **今の制限:** キーを打つたびに表示がいったん読み(かな)に戻り、待ち時間のあとに変換結果へ変わる。変換済みの部分を保ったまま続きを打てるようにする改良は、まだ入れていない。

### 新しい機能の既定値

- **質問:** ライブ変換と状態インジケータを、既定でオンにするか。
- **答え:** 既定はオフにし、設定画面のチェックボックスで有効にする。
- **ほかの選択肢:** 既定でオンにする。Mozc 本家のテストは既定の設定での挙動を前提にしているので、既定を変えると本家のテストの意味が変わり、取り込みのたびに直すことになる。

### 通信定義の番号

- **質問:** Nagi が足す項目の番号をどう決めるか。
- **答え:** 設定、コマンド、出力のいずれも 2000 番台を使う。
- **ほかの選択肢:** 本家の続き番号を使う(Mozkey の方式)。本家が同じ番号を後から使うと衝突する。

### 状態インジケータを描く場所

- **質問:** インジケータを、描画専用のプロセスと IME 本体のどちらで描くか。
- **答え:** IME 本体のプロセスで、小さなパネルとして描く。状態はセッションが `Output.conversion_status` として出力し、クライアントは表示するだけにする。
- **ほかの選択肢:** Mozkey と同じく描画プロセスで描く。候補ウィンドウとの位置調整はしやすいが、プロセス間の命令と配置の計算が増える。まず動く形を優先した。
- **見た目:** `docs/nagi/images/` に、明るい外観と暗い外観の見本がある。テスト `//mac:conversion_status_indicator_test` を `--test_env=NAGI_INDICATOR_SAMPLE_DIR=<保存先>` 付きで実行すると作り直せる。

### Zenz をどう動かすか

- **質問:** Zenz のモデルを、どのプロセスでどう実行するか。
- **答え:** 変換プロセスが `llama-server` を子プロセスとして起動し、この Mac の中だけで通じる HTTP(127.0.0.1)で問い合わせる。問い合わせは別スレッドで行い、最新の 1 件だけを保つ。入力が進んだら、実行中の問い合わせは接続を切って中止する。
- **ほかの選択肢:**
  - Mozkey と同じく、専用の仲介プロセス(scorer)をもう 1 つ挟む。プロセスの寿命の管理は堅くなるが、コードが大きく増える。
  - llama.cpp を変換プロセスにライブラリとして組み込む。プロセス間の通信はなくなるが、ビルドの統合が重い。速さの差は、困ってから測ればよい。
- **子プロセスの後始末:** 使うたびに終了を確認して回収する。変換プロセスの終了時に止める。異常終了で残ったものは、次の起動時に pid ファイルを見て止める。

### Zenz の実行環境の置き場所

- **質問:** パッチを当てた `llama-server` とモデルを、パッケージに入れるか。
- **答え:** 入れない。`src/mac/zenz_runtime/setup_zenz_runtime.sh` が、設定フォルダ(`~/Library/Application Support/Nagi/zenz`)にビルドして置く。
- **ほかの選択肢:** Mozkey と同じくパッケージに同梱する。配布するなら必要だが、ビルドの手順と検査が増える。自分用の今は後回しにした。
- **補足:** 素の llama.cpp(Homebrew のもの)は、Zenz のモデルを読み込めなかった。トークナイザ名を認識させる 1 行のパッチが必要で、パッチと固定する版は Mozkey に合わせた。

### Zenz の結果の表示と確定

- **質問:** Zenz が返した文字列を、Mozc の変換とどう共存させるか。
- **答え:** Mozc の変換状態はそのまま保ち、表示だけを Zenz の文字列に差し替える。Enter では、その文字列を直接確定する。Space では Zenz の文字列を捨てて、Mozc の通常の変換に移る。
- **ほかの選択肢:** Zenz の結果を制約にして Mozc の変換をやり直す(azooKey の Zenzai の方式)。文節の操作や学習がそのまま使えるが、変換エンジンの内部に手を入れる必要がある。
- **今の制限:** Zenz の文字列で確定したものは、Mozc の履歴に学習されない。Zenz と Mozc が同じ結果のときは Mozc の変換として確定するので、学習される。
- **決めたルール:** プレビューの表示中は、どの応答でも同じ内容を出す。表示と Enter で確定される文字が食い違わないことを、テストで確かめている。

### Zenz の結果を採用する条件

- **質問:** Zenz の結果を、どんなときに採用するか。
- **答え:** 結果に含まれるかな(ひらがな、カタカナ、長音、句読点)が、読みの中に同じ順で現れるときだけ採用する。文字数が読みを大きく超えるもの、制御文字やプロンプトの区切り文字を含むものは捨てる。読みがひらがなと句読点だけのときに限り、問い合わせる。
- **ほかの選択肢:** Mozkey のように、固有名詞や数字の保護、絵文字の抑制、採用と却下の学習まで作り込む。効果は大きいが、実際に使って困った例を見てから足す。
- **今の制限:** 漢字の選び方が正しいかは確かめていない。Mozc のほうが良い結果を、Zenz が悪いほうへ変えることがある(例: 「帰社した」を「記者した」に変える)。

### Zenz の結果を受け取る方法

- **質問:** 別スレッドで出た結果を、どうやって画面に反映するか。
- **答え:** ライブ変換と同じ遅延コールバックを使い、クライアントが約 30 ミリ秒おきに `APPLY_ZENZ_CORRECTION` を送って確認する。約 3 秒で打ち切る。
- **ほかの選択肢:** 変換プロセスからクライアントへ通知を送る。待ち時間は減るが、Mozc にはサーバーからクライアントへ送る経路がなく、新しく作ることになる。
- **補足:** 同じ未確定文字列が繰り返し届いても、Mac 側は描き直さない。

### 画面に出る製品名

- **質問:** 設定画面などのタイトルに出る「Mozc」を変えるか。
- **答え:** 「Nagi」に変える(`GuiUtil::ProductName`)。
- **ほかの選択肢:** そのままにする。Mozc や Mozkey の設定画面と見分けがつかなくなる。

### ライブ変換の表示中のサジェスト

- **質問:** ライブ変換の表示中に、サジェスト(文全体の別案)をどう出すか。Mozc は変換中にサジェストを出さないので、何もしないと消える。
- **答え:** ライブ変換を当てる直前に画面に出ていたサジェストを控えておき、表示中の出力に付け直す。Tab やクリックで選ばれたら、読みの状態に戻してから Mozc の通常の処理に渡す。
- **ほかの選択肢:** Mozkey の方式。セッションの状態を丸ごと複製し、複製の上でサジェストを作り直して保持する。選んだときは複製に切り替える。読みが変わらない間の別案を作り直せるが、状態を 2 つ持つぶん壊れやすい。
- **決めたルール:**
  - 表示中に出すのはサジェストだけ。Mozc の変換候補の窓は、入力ミスの訂正案があっても出さない。
  - Zenz の結果を待つ間も、サジェストの内容は変えない。
  - 作者の希望(2026-11-18): Mozkey と同じ体験にする。

### 既定値を Mozkey に合わせる

- **質問:** ライブ変換、状態インジケータ、Zenz の補正を、既定でオンにするか。待ち時間をいくつにするか。
- **答え:** 3 つとも既定でオンにする。ライブ変換の待ち時間は Mozkey と同じ 228 ミリ秒、Zenz の待ち時間は 500 ミリ秒(Mozkey は 700 ミリ秒)。上の「新しい機能の既定値」の判断(既定はオフ)を、作者の指示(2026-11-18)で改めた。
- **入れ方:** 通信定義の既定はオフのまま残し、設定を読み書きする場所で「保存されていなければオンにする」。Mozkey と同じ方式。設定画面の「初期値に戻す」も同じ値になる。待ち時間は Nagi 独自の項目なので、通信定義の既定を直接変えた。
- **ほかの選択肢:** 通信定義の既定をオンにする。設定を何も入れずに作ったセッションでもライブ変換が動き、Mozc 本家のテストの前提が崩れる。
- **本家のテストへの影響:** 台本テストの共通の準備で、3 つをオフにしている。本家のテストは「これらがない挙動」を書いたものだから。
- **補足:** すでに保存した設定には効かない。設定画面は OK で全項目を保存するので、以前の値(オフ、200、0)が残る。「初期値に戻す」か、手で直す。

### 開発中に行った、リポジトリの外への操作

- `~/Library/Application Support/Nagi/zenz` に、Zenz の実行環境を置いた(上のスクリプトを実行)。
- `~/Library/Caches/nagi-zenz-build` に、llama.cpp のビルドの作業フォルダがある。消してよい。
- Homebrew で `bazelisk`、`cmake`、`llama.cpp` を入れた。`llama.cpp` は Zenz のモデルを読み込めず、Nagi では使っていない。
- GitHub で、作者の判断により、Mozkey のフォークを削除して google/mozc のフォークを作り直した。同じアカウントでは、同じ系統のフォークを 1 つしか持てないため。
