# Nagi の判断の記録

開発中に出た判断の要る点を、質問、選んだ答え、ほかにあった選択肢の形で残す。新しいものを下に足す。

## 2026-11-18

### 土台をどう作るか

- **質問:** Nagi を何の上に作るか。
- **答え:** google/mozc をフォークする。Mozkey(koyasi777/mozkey)は実装の手本として読む。
- **ほかの選択肢:**
  - Mozkey をフォークする。気に入っている挙動がそのまま残るが、自分で作る部分が減る。
  - 外側を Swift で一から書き、変換だけ Mozkey のものを外から呼ぶ。検証したところ、Mozkey の補強辞書はリポジトリに含まれず手元で生成する仕組みで、変換部分だけのビルドが通らなかった。
- **決めた人:** 作者。

### 対象の OS

- **質問:** Windows と Linux のコードを消すか。
- **答え:** 消さない。対象は Apple Silicon の Mac だけだが、ほかの OS のコードは Mac 向けのビルドでは使われない。消すと本家の取り込みで衝突するだけになる。
- **ほかの選択肢:** 消して Mac 専用のツリーにする。本家への追従をやめると決めたときに行えばよい。

### 辞書

- **質問:** 辞書をどう持つか。
- **答え:** Mozc の標準辞書を使う。既存の OSS 辞書をスクリプトで取り込むのはよい。Nagi 独自の辞書を作って手で保守することはしない。
- **ほかの選択肢:** 独自の単語リストを育てる。保守の負担が続くので採らない。
- **決めた人:** 作者。

### GitHub 上の形

- **質問:** リポジトリを google/mozc のフォークとして作るか。
- **答え:** 公開のフォークにする。本家は `upstream`、自分の push 先は `origin`。作業ブランチは `main`。
- **ほかの選択肢:** フォーク表示のない非公開リポジトリに履歴ごと push する。取り込みは同じようにできるが、作者がフォーク表示のある見た目を選んだ。

### 名前と識別子

- **質問:** Mozc や Mozkey と同じ Mac に並べて入れるために、何を変えるか。
- **答え:** アプリ名を `Nagi`、識別子の接頭辞を `org.nagi.inputmethod.Japanese`、設定フォルダを `~/Library/Application Support/Nagi`、パッケージの識別子を `org.nagi.pkg.JapaneseInput` にする。ソース内の名前空間、ビルドターゲット名、`BRANDING` は `Mozc` のまま残す。
- **ほかの選択肢:**
  - 接頭辞を `io.github.<アカウント名>.nagi` にする。持っているドメインに基づく正しい逆引き形式だが、アカウント名を変えると識別子も変わる。
  - ソース内の名前もすべて `Nagi` に置き換える。本家の取り込みのたびに衝突するので採らない。
- **根拠:** Mozkey と Mozless が同じやり方で並行インストールを実現している。

### Bazel がヘッダーの変更を拾わない件

- **質問:** この開発環境(Xcode 27.2、Bazel 9.0.2)では、`.h` を書き換えても、それを取り込む `.cc` や `.mm` が再コンパイルされない。`base/const.h` の名前を変えたのに、古い名前が実行ファイルに残った。`.cc` の変更は正しく検知される。どう対処するか。
- **答え:** ヘッダーを書き換えたあとは、自前コードのオブジェクトを消してからビルドする。

  ```sh
  cd src
  find -L bazel-out/ -path '*/_objs/*' -name '*.o' -not -path '*/external/*' -delete
  ```

  名前や識別子に関わる変更のあとは、展開したパッケージの実行ファイルを `strings` で検査して確かめる。
- **ほかの選択肢:**
  - 毎回 `bazelisk clean` する。確実だが、全体のビルドに 10 分以上かかる。
  - 原因を突き止めて直す。コンパイル処理の入力にはヘッダーが宣言されており、Bazel の再起動やファイル監視の切り替えでも直らなかった。原因は未特定で、後回しにした。

### ライブ変換の作り

- **質問:** 遅延付きライブ変換を、どの層にどう入れるか。
- **答え:** Mozc に元からある「遅延コールバック」(`Output.callback` と `delay_millisec`)を使う。キー入力のたびにセッションが `APPLY_LIVE_CONVERSION` を予約し、クライアントが待ち時間のあとに送り返す。キーごとに世代番号を進め、古い予約は捨てる。
- **ほかの選択肢:**
  - クライアント側だけで変換を呼ぶ。セッションの状態と食い違いやすい。
  - Mozkey の実装を取り込む。セッション層だけで 5 万行を超える差分があり、自分で作る方針に合わない。
- **決めたルール:**
  - プレビュー中の文字入力、Backspace、Delete は、読みに対する編集として扱う。
  - Space、文節の操作、確定は通常の変換として扱い、以後は書き換えない。
  - Esc でかなに戻した読みは、読みが変わるまで自動では変換し直さない。
  - 読みが最小文字数より短いとき、ローマ字が途中のときは変換しない。
- **今の制限:** キーを打つたびに表示がいったん読み(かな)に戻り、待ち時間のあとに変換結果へ変わる。変換済みの部分を保ったまま続きを打てるようにする改良は、まだ入れていない。

### 新しい機能の既定値

- **質問:** ライブ変換と状態インジケータを、既定でオンにするか。
- **答え:** 既定はオフにし、設定画面のチェックボックスで有効にする。
- **ほかの選択肢:** 既定でオンにする。Mozc 本家のテストは既定の設定での挙動を前提にしているので、既定を変えると本家のテストの意味が変わり、取り込みのたびに直すことになる。

### 通信定義の番号

- **質問:** Nagi が足す項目の番号をどう決めるか。
- **答え:** 設定、コマンド、出力のいずれも 2000 番台を使う。
- **ほかの選択肢:** 本家の続き番号を使う(Mozkey の方式)。本家が同じ番号を後から使うと衝突する。

### 状態インジケータを描く場所

- **質問:** インジケータを、描画専用のプロセスと IME 本体のどちらで描くか。
- **答え:** IME 本体のプロセスで、小さなパネルとして描く。状態はセッションが `Output.conversion_status` として出力し、クライアントは表示するだけにする。
- **ほかの選択肢:** Mozkey と同じく描画プロセスで描く。候補ウィンドウとの位置調整はしやすいが、プロセス間の命令と配置の計算が増える。まず動く形を優先した。
- **見た目:** `docs/nagi/images/` に、明るい外観と暗い外観の見本がある。テスト `//mac:conversion_status_indicator_test` を `--test_env=NAGI_INDICATOR_SAMPLE_DIR=<保存先>` 付きで実行すると作り直せる。

### Zenz をどう動かすか

- **質問:** Zenz のモデルを、どのプロセスでどう実行するか。
- **答え:** 変換プロセスが `llama-server` を子プロセスとして起動し、この Mac の中だけで通じる HTTP(127.0.0.1)で問い合わせる。問い合わせは別スレッドで行い、最新の 1 件だけを保つ。入力が進んだら、実行中の問い合わせは接続を切って中止する。
- **ほかの選択肢:**
  - Mozkey と同じく、専用の仲介プロセス(scorer)をもう 1 つ挟む。プロセスの寿命の管理は堅くなるが、コードが大きく増える。
  - llama.cpp を変換プロセスにライブラリとして組み込む。プロセス間の通信はなくなるが、ビルドの統合が重い。速さの差は、困ってから測ればよい。
- **子プロセスの後始末:** 使うたびに終了を確認して回収する。変換プロセスの終了時に止める。異常終了で残ったものは、次の起動時に pid ファイルを見て止める。

### Zenz の実行環境の置き場所

- **質問:** パッチを当てた `llama-server` とモデルを、パッケージに入れるか。
- **答え:** 入れない。`src/mac/zenz_runtime/setup_zenz_runtime.sh` が、設定フォルダ(`~/Library/Application Support/Nagi/zenz`)にビルドして置く。
- **ほかの選択肢:** Mozkey と同じくパッケージに同梱する。配布するなら必要だが、ビルドの手順と検査が増える。自分用の今は後回しにした。
- **補足:** 素の llama.cpp(Homebrew のもの)は、Zenz のモデルを読み込めなかった。トークナイザ名を認識させる 1 行のパッチが必要で、パッチと固定する版は Mozkey に合わせた。

### Zenz の結果の表示と確定

- **質問:** Zenz が返した文字列を、Mozc の変換とどう共存させるか。
- **答え:** Mozc の変換状態はそのまま保ち、表示だけを Zenz の文字列に差し替える。Enter では、その文字列を直接確定する。Space では Zenz の文字列を捨てて、Mozc の通常の変換に移る。
- **ほかの選択肢:** Zenz の結果を制約にして Mozc の変換をやり直す(azooKey の Zenzai の方式)。文節の操作や学習がそのまま使えるが、変換エンジンの内部に手を入れる必要がある。
- **今の制限:** Zenz の文字列で確定したものは、Mozc の履歴に学習されない。Zenz と Mozc が同じ結果のときは Mozc の変換として確定するので、学習される。
- **決めたルール:** プレビューの表示中は、どの応答でも同じ内容を出す。表示と Enter で確定される文字が食い違わないことを、テストで確かめている。

### Zenz の結果を採用する条件

- **質問:** Zenz の結果を、どんなときに採用するか。
- **答え:** 結果に含まれるかな(ひらがな、カタカナ、長音、句読点)が、読みの中に同じ順で現れるときだけ採用する。文字数が読みを大きく超えるもの、制御文字やプロンプトの区切り文字を含むものは捨てる。読みがひらがなと句読点だけのときに限り、問い合わせる。
- **ほかの選択肢:** Mozkey のように、固有名詞や数字の保護、絵文字の抑制、採用と却下の学習まで作り込む。効果は大きいが、実際に使って困った例を見てから足す。
- **今の制限:** 漢字の選び方が正しいかは確かめていない。Mozc のほうが良い結果を、Zenz が悪いほうへ変えることがある(例: 「帰社した」を「記者した」に変える)。

### Zenz の結果を受け取る方法

- **質問:** 別スレッドで出た結果を、どうやって画面に反映するか。
- **答え:** ライブ変換と同じ遅延コールバックを使い、クライアントが約 30 ミリ秒おきに `APPLY_ZENZ_CORRECTION` を送って確認する。約 3 秒で打ち切る。
- **ほかの選択肢:** 変換プロセスからクライアントへ通知を送る。待ち時間は減るが、Mozc にはサーバーからクライアントへ送る経路がなく、新しく作ることになる。
- **補足:** 同じ未確定文字列が繰り返し届いても、Mac 側は描き直さない。

### 画面に出る製品名

- **質問:** 設定画面などのタイトルに出る「Mozc」を変えるか。
- **答え:** 「Nagi」に変える(`GuiUtil::ProductName`)。
- **ほかの選択肢:** そのままにする。Mozc や Mozkey の設定画面と見分けがつかなくなる。

### ライブ変換の表示中のサジェスト

- **質問:** ライブ変換の表示中に、サジェスト(文全体の別案)をどう出すか。Mozc は変換中にサジェストを出さないので、何もしないと消える。
- **答え:** ライブ変換を当てる直前に画面に出ていたサジェストを控えておき、表示中の出力に付け直す。Tab やクリックで選ばれたら、読みの状態に戻してから Mozc の通常の処理に渡す。
- **ほかの選択肢:** Mozkey の方式。セッションの状態を丸ごと複製し、複製の上でサジェストを作り直して保持する。選んだときは複製に切り替える。読みが変わらない間の別案を作り直せるが、状態を 2 つ持つぶん壊れやすい。
- **決めたルール:**
  - 表示中に出すのはサジェストだけ。Mozc の変換候補の窓は、入力ミスの訂正案があっても出さない。
  - Zenz の結果を待つ間も、サジェストの内容は変えない。
  - 作者の希望(2026-11-18): Mozkey と同じ体験にする。

### 既定値を Mozkey に合わせる

- **質問:** ライブ変換、状態インジケータ、Zenz の補正を、既定でオンにするか。待ち時間をいくつにするか。
- **答え:** 3 つとも既定でオンにする。ライブ変換の待ち時間は Mozkey と同じ 228 ミリ秒、Zenz の待ち時間は 500 ミリ秒(Mozkey は 700 ミリ秒)。上の「新しい機能の既定値」の判断(既定はオフ)を、作者の指示(2026-11-18)で改めた。
- **入れ方:** 通信定義の既定はオフのまま残し、設定を読み書きする場所で「保存されていなければオンにする」。Mozkey と同じ方式。設定画面の「初期値に戻す」も同じ値になる。待ち時間は Nagi 独自の項目なので、通信定義の既定を直接変えた。
- **ほかの選択肢:** 通信定義の既定をオンにする。設定を何も入れずに作ったセッションでもライブ変換が動き、Mozc 本家のテストの前提が崩れる。
- **本家のテストへの影響:** 台本テストの共通の準備で、3 つをオフにしている。本家のテストは「これらがない挙動」を書いたものだから。
- **補足:** すでに保存した設定には効かない。設定画面は OK で全項目を保存するので、以前の値(オフ、200、0)が残る。「初期値に戻す」か、手で直す。

### 打ち続けたときに変換済みの部分を保つ

- **質問:** ライブ変換のあとに続きを打つと、全体がかなに戻っていた。Mozkey のように変換済みの部分を保つには、どう作るか。
- **答え:** ライブ変換から抜けるときに、「かな」と「変換結果」の組を文節ごとに控える。読みの状態の出力を作るたびに、いまのかなの先頭と一致する組だけを変換結果に置き換える。出力を作る場所は 1 つの関数にまとめ、キーのない出力でも同じ表示になるようにした。
- **ほかの選択肢:** Mozkey の作り。表示用の状態、Zenz の表示の区切り、古い表示からの救済などを別々に持つ。細かい場面まで保てるが、状態が多い。困った場面が出てから足す。
- **決めたルール:**
  - 文節は分割しない。一致しなくなった文節と、それより後ろは、かなに戻す。
  - 照合は、変換の直前に画面に出ていたかなで行う。変換用の読みは使わない(末尾の「ｎ」が「ん」になるなど、画面のかなと食い違う)。
  - Zenz の結果を表示していたときは、全体を 1 つの組として保つ。一致しなくなったら Mozc の文節に落とす。
  - 控えを残すのは、文字入力、Backspace、Delete で抜けたときだけ。確定、Esc、Space では消す。
  - この状態の Enter は、見えている文字をそのまま確定する。学習はしない(Mozkey も同じ)。
- **インジケータ:** 読みが変換の対象になった時点で「Mozc」を出す(Mozkey と同じ)。「入力中」は、読みが最小文字数に届かない間だけ。

### インジケータの決まりを Mozkey に合わせる

- **質問:** どの場面でどの表示を出すか。
- **答え:** Mozkey と同じにする(作者の指示、2026-11-18)。
  - 未確定の文字がなければ出さない。
  - Zenz に問い合わせる予定、または問い合わせ中なら「Zenz…」。待ち時間のあいだも含む。
  - Zenz が文字を書き換えたら「Zenz」。同じ結果なら「Mozc」。
  - ライブ変換の表示中と、変換の対象になった読みを打っているあいだは「Mozc」。
  - 読みが最小文字数に届かないあいだは「入力中」。
  - Space や Tab で候補を選んでいるあいだは出さない。
- **ほかの選択肢:** 「Zenz…」を実際の問い合わせ中だけにする。一度そうしたが、Zenz の応答が数十ミリ秒と速く、一瞬光るだけになった。作者が元に戻すと決めた。
- **Mozkey との違い:** Mozkey は候補の窓が見えているかどうかで隠す。Nagi は、自分で変換を始めた状態かどうかで隠す。Nagi は最初の Space で窓を開かないので、同じ判定だと変換中に「入力中」と出てしまう。

### 辞書を Mozkey と同じ構成で強化する

- **質問:** システム辞書をどう強化するか。
- **答え:** Mozkey が配布版(daily)で足している 4 つを、同じ版で足す。地名と SudachiDict の語彙、人名、ニコニコ・pixiv 系の固有名詞、区切りを保護する語。作者の指示(2026-11-18):「mozkeyと同じようにこれ入れようよ」。
- **入れ方:** `tools/dictionary/prepare_dictionary.sh` が、Mozkey を固定したコミットで取得し、その中の道具(取得元の固定、絞り込み、検査、区切りの保護)を書き換えずに動かす。重複を除く基準と品詞の番号には、Nagi の Mozc 辞書を使う。できた辞書はリポジトリに入れない。
- **ほかの選択肢:**
  - SudachiDict だけを素のまま足す。Mozkey は重複の除去、コストの付け直し、区切りの保護を通している。それを省くと、Mozkey とは別の結果になる。
  - Mozkey の道具を Nagi に写して持つ。書き換えられるが、Nagi が保守する辞書の仕組みになる。辞書の方針(自分で作って保守しない)に反する。
- **辞書の方針との関係:** 区切りを保護する語と絞り込みの規則は手書きだが、書いて保守しているのは Mozkey の作者。Nagi は版を上げて取り込み直すだけにする。
- **確かめたこと:** 入れる前後で 15 文を流した。Mozc だけの変換は 3 文が良くなり(「した方がいい」「昨日の会議」「にまで」)、悪くなった文はなかった。Zenz を通した結果は 15 文とも同じ。辞書に関わるテストは、入れた状態で通る。
- **変わること:** パッケージは約 42MB から約 54MB になる。
- **今の制限:**
  - 同じになるのは辞書で、変換結果ではない。Mozkey は変換や候補の並べ替えにも手を入れている。
  - 区切りを保護する語の生成で、元になる語が見つからない件数が出る(と: 156、に: 92)。Mozkey の Mozc 辞書で作った場合と同じかは調べていない。
  - この環境の Bazel は、辞書を埋め込むファイルの変更を検知しない。スクリプトが、該当するオブジェクトを消している。

### Zenz の結果を採用する条件を足す(#2)

- **質問:** Zenz が Mozc の変換を悪いほうへ書き換えるのを、どう減らすか。
- **調べたこと:**
  - 同音異義語の多い 40 文と、人名・地名の 30 文を、Zenz ありとなしで流した(`tools/zenz_compare.sh`、`tools/zenz_cases/`)。Zenz が変えたのは 25 文。良くなったのが 15 前後、悪くなったのは 3 文(「記者が帰社した」を「記者が記者した」、「恵比寿」を「えびす」、「さゆり」を「さユり」)。
  - Mozkey の採用条件を読んだ。同音異義語の入れ替えを止める規則は Mozkey にもない。コストも候補の一覧も使っていない。止めているのは、利用者が差し戻した記録だけ。
- **答え:** 規則で塞げる穴だけを塞ぐ。`zenz::KeepsEngineText` を足し、次のときは Mozc の変換を残す。
  - Zenz の結果が、Mozc の変換の先頭か末尾だけになっている(打った文字が欠ける)。
  - 英数字の並びや絵文字が、Mozc の変換と違う(Zenz が作ったか、書き換えた)。
  - Mozc が選んだユーザー辞書の語が、結果に残っていない。
- **入れなかったもの:**
  - 同音異義語で Mozc を優先する規則。Zenz が良くした例の大半が同じ型の入れ替えなので、足すと改善のほうが先に消える。
  - システム辞書の固有名詞の保護。Mozkey は、曖昧な読み約 110 件と地名の組約 60 件の例外を手で持っている。30 文で壊れた名前は 2 つで、片方は同じ文の別の箇所を Zenz が直していた。保守の重さに見合う証拠がまだない。
  - 差し戻しの記録(Space で Mozc に戻した補正を、次から出さない)。「記者」の例に効くのはこれだけだが、打った文字を保存する話なので、#3 と一緒に決める。
- **確かめたこと:** 足す前後で 70 文の結果は同じ。Zenz の良い補正は消えていない。

### Zenz の補正の採用と差し戻しを覚える(#3)

- **質問:** Zenz の補正について、利用者がしたことをどう次に活かすか。
- **答え:** 読みと補正結果の組を、`~/Library/Application Support/Nagi/zenz_feedback.tsv` に記録する(`zenz/zenz_feedback`)。
  - Enter で確定した補正は「採用」。次に同じ読みを変換したとき、Zenz に問い合わせずにすぐ出す。
  - Space などで Mozc の変換に戻した補正は「差し戻し」。その読みでは、次から出さない。
  - 同じ組については、新しいほうの判断が勝つ。
- **置き場所:** Mozc の履歴と同じ設定フォルダ。作者の指示(2026-11-18):「置き場所はベストだと思うところにして」。設定や辞書と一緒にバックアップでき、Nagi を消すときも 1 か所で済む。Mozkey も同じ場所に同じ名前で置いている。
- **外に出さない:** 記録はこの Mac の中だけ。作者の確認(2026-11-18):「ローカルファーストというかローカル簡潔なのは変わらないよね？だったらやっていいよ」。
- **記録しない場面:** シークレットモードでは、記録も呼び出しもしない。パスワード欄は、そもそも Zenz に問い合わせない。
- **ほかの選択肢:**
  - メモリの中だけで覚える。更新や再ログインのたびに消えるので、開発中はほぼ効かない。
  - 採用した補正を Mozc 本体の履歴にも教える(Mozkey はしている)。同じ文でなくても効くようになるが、エンジンの学習の入口に手を入れる必要がある。まず読み全体の一致で使ってみて、足りなければ足す。
- **今の制限:**
  - 効くのは、読み全体が同じときだけ。その語を含む別の文には効かない。
  - 記録は平文。Mozc の履歴は暗号化されているが、鍵は同じフォルダにあり、同じ Mac の中では守られない点は変わらない。
  - 気づかずに Enter で確定した間違いも「採用」として残る。次に Space で戻せば、差し戻しが勝つ。
  - 上限は 5,000 件。超えたら古いものから消す。

### 自動入力モードの判定の作り(#1、作業中)

入力の処理には、まだつないでいない。判定だけを作って測っている段階。

- **質問:** 打ったキー列のどこが英語かを、どう決めるか。
- **答え:** 変換器に決めさせる。「かなとして変換したコスト」と「ある語を英字にして変換したコスト」を比べ、英字にしても大きく悪くならない語を英語とする(`src/english/english_detector`)。1 語選ぶたびに、残りをもう一度比べる。
- **ほかの選択肢:**
  - 英単語の一覧に載っているかだけで決める。`homeru`(褒める)の中の home のように、日本語の途中で英字に化ける。
  - その場で一番よさそうな 1 語を選ぶ(Python の試作)。英単語が 2 つある文と、子音で終わる語を扱えなかった。
- **決めたルール:**
  - ローマ字として読めない語は、ゆるい条件で英語にする。読める語(time、made)は、語だけのコストが高く、文に入れても大きく悪くならないときだけ英語にする。
  - 打っている最中は、末尾の子音を次の音の打ちかけとして扱う(`git` は `gita` に続くかもしれない)。変換や確定の直前は、打ちかけとして扱わない。
  - 日本語として読めなくなったら、打ちかけの英単語を打ったまま見せる。
  - 日本語として読めるあいだは、変換器が切った文節の境目からしか英単語を始めない。「しらせ」の中の rase を英語にしないため。
  - 同じく、英単語にしようとしている部分がかかる文節が、どれも日本語として自然(文節のコストが 10,000 未満)なら、英語にしない。「まだ|めに」の中の madame を英語にしないため。「ちめを|はかる」の「ちめを」は不自然なので、time の候補になる。
  - 英単語を 2 つ続けて選ばない。変換器には 1 つの未知語に見えて、どんな組でも安く見えるため。
  - 長い入力では、末尾の 40 打鍵だけを見直す。それより前に決めた英単語は動かさない。
  - 打ち終えてから 12 打鍵たった英単語は、見直さない。見直すたびに手前の文脈が短くなり、1 回でも判定が外れると英単語がかなに戻って、そのまま窓の外へ出るため。長い入力での取りこぼしは、これで 21.7% から 11.8% になった(毎回すべて見直すと 13.2% で、1 打鍵に最大 374 ミリ秒かかる)。引き換えに、誤判定が 12 打鍵続くと残る。
  - 辞書にしか載っていない、ローマ字の人名(ayaka、kotoko)は、英単語の一覧から外す。
- **英単語の一覧:** SCOWL、cspell-dicts、変換辞書の英字の語から、`tools/english/prepare_english_words.sh` で作る。約 16 万語。手で書いた語はない。リポジトリには入れない。
- **測り方:** `tools/english/measure/run_detector.py`。入力を 1 打鍵ずつ流し、最後の表示が正しいかと、途中で誤って英字が出たか(ちらつき)を数える。
  - 日本語: Mozc 本家の評価用の読み、辞書の語(頻度順)、JSUT basic5000 の文(本文を逆変換して読みにしたもの)。
  - 英語入り: 英単語を言い回しに差し込んだもの。Mozless の手書きの 78 文と 80 文。実際の文 2 つのあいだに英単語を挟んだ長い入力。
- **測定の結果(2026-11-18、入力の処理につなぐ前):**

  | 流したもの | 件数 | 最後まで誤ったもの | ちらつきのあった入力 | ちらつきのあった打鍵 |
  |---|---|---|---|---|
  | 日本語の語(辞書の頻度順) | 19,412 | 0 | 8(0.04%) | 0.01% |
  | 日本語の文(Mozc 本家の評価用) | 1,254 | 2(0.16%) | 1 | 0.01% |

  | 日本語(Mozless の 80 文) | 80 | 0 | 0 | 0 |
  | 英語入り(一覧の全域から選んだ語) | 3,000 | 247(8.2%) | 567(18.9%) | 2.57% |

  - **どの数字も、規則を決めるのに使った入力でのもの。** しきい値は、実際の文章の誤りを見ながら決めた。Mozless の文も、取りこぼした語(time、file、login)を見て条件を直したので、手を付けていない検証用ではなくなった。初めて見る文章では、これより悪いはず。

### 自動入力モードを入力の処理につなぐ(#1、作業中)

- **質問:** 判定の結果を、打っている文字にどう反映するか。
- **答え:** 判定が変わるたびに、composer の中身を打鍵から作り直す(`english::TypeWithRuns`)。英単語は composer の半角英数モードで、ほかはローマ字として入れ直す。表示、変換に渡す読み、確定する文字が、どれも同じ中身から出る。
- **ほかの選択肢:** 表示と読みを、出口で別々に書き換える。composer を読む場所が 10 ファイルあり、書き換え漏れが出る。
- **決めたこと:**
  - 設定は `use_automatic_english`、既定はオフ。設定画面の「ライブ変換」タブの最後に置いた。
  - 変換(Space)と確定(Enter)の直前に、もう一度判定する。末尾の子音がもうかなにならないので、`git` + Enter は `git` になる。
  - 対象は、入力の末尾で打っている小文字のローマ字だけ。大文字が入った入力と、カーソルを動かした入力は、そのままにする。
  - 数字と `,.!?` は、ローマ字の区切りとして扱う。区切りの前は、打ち終えたものとして判定する(`git.` の git は英字)。
  - 前の判定を使い回すのは、キーが 1 つ増えたときだけ。Backspace のあとは、最初から判定し直す。
  - 英単語の一覧は、ビルドのときにバイナリに埋め込む。一覧を作っていないビルドでは、何もしない。
  - 単語の前の、母音を待っている `n` は「ん」にする(`hangoogle` は「はんgoogle」)。
  - 入力の末尾が、一覧にある英単語で終わっているときは、打鍵が止まればライブ変換を始める(`kyouhagoogle` で止まると「今日はgoogle」)。それまでは、末尾が英字だと打ちかけとみなして始めなかった。
- **変換中の英字の既定を、半角にした。**
  - **質問:** 辞書に英字で載っていない語(push など)が、変換すると全角(ｐｕｓｈ)になる。どうするか。
  - **答え:** 設定の「変換中のアルファベット」の既定を、Mozc の「直前の形を覚える」から「半角」に変えた(`config_handler.cc`)。自動入力に限らず、すべての変換に効く。
  - **理由:** 「直前の形を覚える」は、最初は全角で始まる。ライブ変換で全角のまま確定すると、全角を覚えてしまう。よく使う英単語を言い回しに入れた 300 件では、35 件が全角になっていた。変えたあとは 0 件。
  - **ほかの選択肢:** 自動入力で英字にした語だけ、半角に固定する。変換器の候補に手を入れる必要があり、大きい。
  - **注意:** すでに設定を保存している環境では、保存済みの値が使われる。設定画面で「アルファベット」の「変換中」を「半角」にする必要がある。
- **確かめ方:** `tools/english/measure/compare_session.py`。実際のセッションに打鍵を流し、確定した文字を判定の道具の結果と比べる。1,358 件が一致した。
- **残っていること:**
  - 入力が `git` のように子音で終わる英単語で止まったときは、ライブ変換が始まらない(打っている最中は、子音を次の音の打ちかけとして扱うため)。Space か Enter を押せば英字になる。
  - 英単語の直後の句読点は「．」「，」になる(`gitでpush.` は「gitでpush．」)。Mozc が、英数字の直後の句読点をそうする決まりのため。
  - セッションの単体テストはない。上の比較で確かめている。

### 自動入力モードで直した語を覚える(#1)

- **質問:** F10 と F6 を、自動入力モードでどう働かせるか。直した結果を、どう覚えるか。
- **答え:** F10 は打ったばかりの 1 語を英字にし、F6 はいちばん後ろの英字の語をかなに戻す。確定したときに、直した語だけを覚える。
- **経緯:**
  - 作者の答えは、直し方が「直前の語を切り替える」、キーが「Mozless と同じ(F10 で英字、F6 でかな)」だった。Mozless を調べると、F10 と F6 に専用の処理はなく、Mozc に元からある「入力全体を切り替える」動きのままだった。
  - いったん Mozless に合わせて入力全体を切り替える形で作り、実際に流して比べた(2026-11-18)。
    - `kyouhanote` + F10 は `kyouhanote` になる。文の途中では役に立たない。
    - `gitdepushsitaatotestsuru` + F6 は、全部がかなになる。確定すると git、push、test の 3 語を「英語ではない」と覚え、正しかった 2 語の学習まで壊した。
  - advisor と相談し、1 語だけを切り替える形に作り直した。作者にも結果を見せて相談中。
- **動き:**
  - F10: 入力の末尾で終わる、いちばん長い英単語(一覧にある語か、覚えた語)を英字にする。その前がかなとして読めることが条件。`kyouhanote` + F10 は「きょうはnote」。
  - F6: いちばん後ろの、英字で見せている語をかなに戻す。ほかの語はそのまま。
  - 切り替えた語は、その入力を確定するまで固定する。あとから打った文字で判定が変わっても、動かさない。
  - 当てはまる語がないときは、Mozc の元の動き(入力全体を切り替える)になる。同じキーをもう一度押したときも同じ。
  - ライブ変換の表示中でも、同じように働く。表示をやめて読みに戻し、語を切り替える。
  - キーは、キー設定で F10 と F6 に割り当ててある命令(半角英数に、ひらがなに)に載せた。キー設定を変えれば、ほかのキーでも働く。
- **覚える決まり(確定したとき):**
  - キーで切り替えた語を覚える。英字にした語が確定した文字に入っていれば「英語」、かなに戻した語が入っていなければ「英語ではない」。
  - キーを使わず、入力全体を打ったとおりの英字で確定したとき(1 語だけの入力に Mozc の元の F10 を使ったとき)は、その入力を「英語」と覚える。ただし、かなとして読めて、どの一覧にもない入力(`handan`)は覚えない。全角の英字(`ｔｈｘ`)で確定したときも覚えない。
  - 英字で見せた語が 1 つだけで、確定した文字にそれが入っていなければ、「英語ではない」と覚える。変換で別の候補を選んだときがこれに当たる。2 語以上あるときは、どの語のことか分からないので覚えない。
  - 覚えないもの: シークレットモード、パスワード欄、ライブ変換の表示をそのまま確定したとき。
- **覚えた語の効き方:**
  - 「英語」と覚えた語は、入力の最後なら必ず英字にする。途中にあるときは、日本語の語の境目から始まり、英字にしても変換のコストが大きく悪くならないときだけ英字にする(`taught_margin`)。`todo` を覚えても「とどかなかった」は変わらない。
  - 境目の条件を外すと、覚えた語がもっと効くが、日本語を壊す。10 語を覚えさせて実際の文章 4,708 件を流すと、誤りが 1 件から 10 件に増えた(「おばのてで」が「おばnoteで」)。外さないことにした。そのため `kyouhanotewotoru` は、note を覚えていても「きょうはのてをとる」になる。
  - 一覧にない語(`kubectl`)も、覚えれば英字になる。
  - 「英語ではない」と覚えた語は、英字にしない。その語に重なる語(`test` に対する `tests`、`totes`)も英字にしない。
- **置き場所:** `~/Library/Application Support/Nagi/english_words.tsv`(`語<TAB>E か J`、3,000 語まで、平文)。設定の「学習履歴のクリア」で消える。外には送らない。
- **確かめたこと:** code、note、time、file、token、image、made、todo、login、release の 10 語を「英語」と覚えさせて測り直した。日本語の誤りは、実際の文章 4,708 件で 1 件のまま。Mozless の英語入り 78 文の取りこぼしは、10 件から 5 件になった。`taught_margin`(12,000)は、この 10 語のコストを見て決めた値。
- **分かっている制限:**
  - `google` は「英語ではない」と覚えさせても英字になる。Mozc が、`google` や `http` と打つと自動で英数に切り替える仕組みを元から持っているため。
  - `gitdepush` のように、子音で終わる語を打った直後は、その語がまだ英字になっていない。そこで F6 を押すと、その前の語(git)がかなに戻る。
